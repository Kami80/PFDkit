# Adding an equipment explorer

An explorer is a trusted renderer and a registry entry reading the same equipment configuration as the PFD. Imported JSON contains data, never executable plugin code, SVG fragments, HTML or URLs to load as renderers.

1. Add a Pydantic configuration model in `packages/pfd-core/src/pfd_core/registry.py`. Use bounded strict numbers, nullable unknown measurements, JSON integer normalization and cross-field validation where needed. Keep existing logical port IDs stable. Describe supported and unsupported arrangements.
2. Register `available_views=["pfd", "explorer"]` and `explorer` content with `views`, `principle`, `components`, `references` and `valueStatus`. Use original text and illustrations, cite primary references, and declare schematic limitations. Symbol/detail/education are capabilities; unsupported equipment has only the PFD view.
3. If ports depend on configuration, extend Python `registry.for_equipment` and TypeScript `equipmentPorts`. Every consumer uses this resolver: validation, connection creation/reconnection, editor handles, symbol geometry and export. Removal of a connected port must fail without mutating the document. A stage-location edit keeps the port and stream IDs.
4. Regenerate the contract with `.venv/Scripts/python scripts/generate_contract.py` and `node scripts/generate_types.mjs`. Add corresponding cross-field invariants to `packages/contracts/src/equipment.ts`; its JSON Schema checks already come from the registry.
5. Add a pure SVG renderer and connected-stream accessor in `apps/web/src/lib`. Escape all document text with `escapeXml`; check own properties for document dictionaries. Include semantic title/description, labels, redundant phase/circuit cues, deterministic bounds and original-art attribution. Avoid fixed-height compression: the column grows 30 units per stage. Use schematic spacing, not an implied mechanical scale.
6. Register the executable implementation in `apps/web/src/lib/explorers.ts`. `EquipmentExplorer` supplies navigation, history, generated configuration controls, operating fields, component explanations, overlays, zoom and export. `readOnly` presentation inspection hides engineering editing. New registry scalar fields appear in both property panels and explorers automatically; extend the shared array controls for a genuinely new nested field structure.
7. Test valid/boundary/unsupported arrangements, nullable properties, dynamic ports, rejected edits, escaped content, saved references, undo/redo, navigation and exported detail. Inspect representative output at its intended physical size.

## Exchanger example

The exchanger renderer supports one to eight representative tube paths, one or two shell passes, zero to twelve baffles, and a one-pass cross-flow schematic. Tube inlet remains the logical `tubeIn` port; an even tube-pass count returns `tubeOut` to the physical inlet side. Circuit colors identify tube/shell, not hot/cold. Relative hot/cold labeling compares entered inlet temperatures after unit conversion, with neither duty nor outlet conditions calculated. Unknown values remain null.

Legacy schema 1.0 documents with larger pass counts, multi-pass cross-flow or more shell than tube passes still load. Their configuration is retained with an unsupported-illustration warning. The shared form rejects newly entered incompatible arrangements; choose a compatible axial arrangement before adding passes. Unknown scalar dimensions remain editable blanks. Baffles and tube/shell dimensions are manually supplied specifications; paths and baffle spacing are conceptual.

## Column example

One to one hundred declared contacting stages are supported. The count always excludes the external condenser and reboiler, including partial units that may be counted differently in other engineering conventions. `stageBasis` explicitly distinguishes actual trays from theoretical stages. Packing displays conceptual contacting locations, not actual tray plates. No efficiency conversion, equilibrium, hydraulic or thermal calculation is performed.

The fixed ports `feed`, `overhead`, `bottoms`, `reflux` and `boilup` retain M2 identities. Additional `feeds` and `sideDraws` use unique stable `portId` values and explicit stage numbers. Multiple connections may share a stage; the illustration fans out numbered F/D labels and lists their full stable IDs. Change stage locations before reducing the count. Connected port removal/rename is rejected until its external stream is disconnected or reconnected. Changing numbering in the shared form remaps every feed, draw and stage-condition number atomically to retain physical locations. Direct JSON numbering edits intentionally obey the supplied stage numbers.

The compact PFD symbol also fans out colliding side handles, including its fixed feed, reflux and boilup. Python and TypeScript use the same deterministic ordering by physical stage offset and stable port ID, with at least six symbol units between handle centers within the 80-unit side. This accommodates twelve additional feeds and twelve side draws, even when all share one stage. Hover labels identify each stable port ID. PFD nozzle locations are schematic spacing; the detail illustration and port names retain the declared stage locations. Changing a stage or adding a port may redistribute nearby PFD handles without changing stream references.

Total/partial/absent condenser and reboiler arrangements are schematic. A total reboiler returns vapor with liquid bottoms withdrawn upstream; the partial reboiler retains a liquid bottoms product. External reflux/boilup ports remain available in all arrangements as logical references. Ratios and stage SI conditions are manual entries, not solved results.

References: [DOE heat transfer handbook](https://www.energy.gov/documents/doe-hdbk-1012-92vol2) and [ETH Zurich Hyper-TVT distillation](https://www.hyper-tvt.ethz.ch/distillation-page.html), especially non-standard distillation, multiple feeds, side draws and stage efficiency. Reference principles inform the original MIT-licensed schematics; source diagrams are not copied.
